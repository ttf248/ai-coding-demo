实验档案维护指南

发布保持不变

仓库根目录就是 GitHub Pages 发布目录。继续使用已有分支自动发布及 CNB → GitHub 同步。提交源码、目录数据和必要的预览产物即可发布；不新增 Actions 发布工作流，不改发布源、域名或同步配置。

index.html、topic.html、compare.html、assets/、previews/ 都是要提交的站点文件。构建缓存、node_modules/、demo 自身的 dist/ 不提交。页面之间使用相对链接，支持域名根目录与 /ai-coding-demo/ 子路径。整体站点使用 HTTP 预览，单 HTML demo 仍可直接打开。

需要后端或独立运行环境的项目继续由维护者人工部署到 Vercel；本站只登记实际地址。不因为目录改造推测这些服务已部署。目录迁移不会自动修改 Vercel 项目设置：迁移后先按 Vercel Root Directory 对照表 更新 Root Directory，再重新部署；原有域名与环境变量保持原配置。股票项目的 Vercel 根目录需要指向 demos/stock-watching/runs/unknown-unknown-r01/frontend/。

目录和唯一事实来源

  • demos/{topic}/topic.json：主题名称、简介、分类、标签。
  • demos/{topic}/prompts/{version}/：不可覆盖的任务正文及来源。
  • demos/{topic}/runs/{run}/run.json：每次实验的模型、档位、日期、输入、产物与预览配置。
  • 每次实验的 prompt.md：完整原始输入快照；Readme.md 保留原始说明、复盘与自动元信息区块。
  • catalog/models.json、categories.json、guides.json：共享字典和技术索引。
  • assets/generated/catalog.js：自动生成的浏览器数据，不手改。
  • assets/core.js：首页、主题页、对比页共用的组件与排序逻辑；assets/home.js、assets/topic.js、assets/compare.js 是各页自己的交互脚本。
  • catalog/tools.json：运行工具及历史名称的明确别名。模型厂商由 models.json 登记，工具或接入平台不作为模型厂商；旧 environment.tool 保留原始名称，新记录可同时填写 environment.toolId。
  • catalog/batches.json：费用批次字典。新实验可使用 billing: {"type":"batch","batchId":"已登记批次"}。既有实验中的完整费用快照继续保留，校验器核对它与字典的一致性。
  • 根 README 的 catalog 区块、主题 README、实验 README 的 archive 区块由脚本维护。区块外的历史记录不会被生成器覆盖。

模型发布日期与排序

模型排序依据保存在 catalog/models.json 的 ordering，契约见 catalog/schema.json 的 modelOrdering。查看完整排序及官方来源核对表，该表及其静态阅读页由 npm run generate 从模型字典生成，禁止手工维护第二份顺序。

厂商内部先按 generation 显式登记的代际从新到旧，再按同代 capabilityRank 从大到小，最后按 releaseDate 从新到旧。代际不直接等同显示版本：GPT-6.1 Sol 与 GPT-6 Astra / Sol / Luna 归入 [6]；Claude Opus / Sonnet / Haiku 5.5 归入 [5, 5]，因此较晚发布的 Haiku 5.5 不会越过同代 Opus / Sonnet。能力优先级依据已保存的官方产品定位和比较作维护判断，仅在同厂商同代比较，不是跨代或跨厂商分数。官方依据只能确认月份时保留 YYYY-MM，不能补造具体日期。缺少日期置于厂商末尾；同代能力未比较的型号置于已登记优先级之后；其余并列保留版本、变体及 ID 的稳定顺序，不表示能力强弱。筛选列表、档位矩阵和对比候选统一使用 ArchiveUI.compareModels，不按显示名称拆解或另排一套顺序。主题页实验记录默认按截图评分排序，模型排序改为显式选择 sort=model 后使用（见主题页浏览）。

releaseDate 记录模型首次官方公布的日期，不是实验日期、知识截止日期、文档修改日期、降价日、区域或第三方平台接入日期。Free 等接入标签可按明确可识别的基础型号首发排序，并在 note 注明边界；不得将正式版日期或能力结论套用到预览检查点。型号不明确或名称与官方不一致时保持原有 ID、名称及历史输入，日期和能力填 null，等待维护者确认。

新增模型前执行 npm run models:pending。输出中的 needsResearch 才需要查询官方消息；已有记录直接复用，包括已明确记为未知的型号。needsConfirmation 是查过但仍需确认的项目，不代表每次都要重新查询。除新增缺失记录或维护者明确要求刷新外，日常生成、校验和浏览都不联网查询模型资料。保存 checkedAt、官方 sources、日期说明 note 和能力依据 capabilityNote；status 分别使用 verified（已确认）、partial（月份确认但日不明确）、unresolved（仍待确认）或 not-applicable（仅 unknown）。不能将未查证和查证后未知混为一谈。

实验费用写在 run.json 的 billing 中。type: "subscription" 记录订阅方式，未知的货币金额填 null；type: "batch" 的 amount 是批次合计，关联批次的多条 run 可重复引用同一 batchId，不得将总额误读或拆算为单案例费用。金额换算时，sourceAmount、sourceUnit 与 conversionRate 保留原始数值及换算比例；amount 和 unit 记录换算结果。平台没有提供的额度或费用明细保持未知，并在 note 说明口径。

所有元数据使用 schemaVersion: 1，契约见 schema。实验 ID 为 {topic}--{run}；目录用小写 kebab-case，显示名称不受 slug 限制。模型重跑新增 r02，不是覆盖 r01。未知模型用 unknown；日期允许年、月、日精度，缺失为 null。

实验日期 date、归档日期 archivedAt、截图日期 screenshotCapturedAt 分别登记。历史未留存的日期保持 null，不得用迁移日期或文件修改时间补造。脚手架只登记实际创建当天的归档日期；有明确来源的重跑或迭代填写 sourceRunId，无来源关系填 null。截图展示尺寸、指纹和缩略图由原始 PNG 自动读取和生成，不修改证据原图。

生成的站点资料

npm run generate 会更新并提交以下静态产物：

  • assets/generated/catalog.js：列表使用的轻量摘要，不包含原始输入和任务正文。
  • assets/generated/topics/*.json：按主题读取的详情，批次费用引用共享字典。
  • assets/generated/inputs/*.json 与 tasks/*.json：按指纹去重的输入和任务正文；仅统一 BOM 与换行，原始 Markdown 不变。查看正文时按需读取，失败可重试。
  • assets/generated/readers/：实验、主题、技术说明与维护文档的静态 HTML 阅读页，保留原文下载、目录、代码复制及相对链接。生成区块标记留在 Markdown 源文档中供生成器更新，但渲染为阅读页时会自动剔除；不要手改生成阅读页或从源文档删除这些标记。缺失的历史附件显示“文件未留存”，原文路径继续保留。
  • assets/generated/screenshots/：从 run 登记的原始 PNG 派生 WebP 资源。按原图宽度生成不超过原图尺寸的 240、480、960 像素缩略图；高宽比大于 1.15 的竖图另生成顶部裁剪的 16:10 封面，宽度为 480 / 960 像素（不超过原图宽度）。文件名含原图指纹，首页按展示槽位和断点选择资源；放大预览和阅读页仍使用完整原始 PNG。
  • assets/generated/vendor/、guide-demos.css 和 guide-react.js：技术示例的本地运行资源、许可证及预编译脚本。技术示例修改后运行 generate 即可；已归档 demo 不统一升级依赖。

导入者只需把实际运行截图 PNG 放入 run 目录并登记 run.json.screenshot，随后执行 npm run generate。截图尺寸、指纹、缩略图及竖图封面均由脚本派生，不能手工制作、登记或修改 assets/generated/screenshots/ 中的文件；派生资源需要和其他生成站点文件一起提交。截图证据本身仍须人工按评分规则复核，缩略图生成不会代替截图评分。

assets/generated/catalog.js 由生成器逐条输出目录记录，每条记录单独一行，便于审阅新增案例只影响哪些条目；不要手工调整输出格式或编辑生成文件。npm run validate 会核对截图派生文件是否存在、生成阅读页是否泄漏区块标记，并执行本站样式文件的重复规则闸门。

新案例导入中的脚本职责

普通导入只维护事实来源和实验产物，再运行下表中的适用命令。首页、主题页与对比页会消费生成数据；无需逐案例增加卡片、排序分支、导航、图片断点或 CSS。公共能力需要变更时才修改对应站点代码并执行交互与样式回归。

命令 自动完成 仍需维护者完成
npm run new:demo -- ... 检查模型和指定提示词是否已登记、拒绝默认追加归档主题、选择下一个 rNN 并创建 draft 文件结构；提示同名主题、同型号模型和同一任务正文的重复登记风险。未指定提示词时会建一个待填写的新版本。 确认脚本提示的重复项；填入真实输入、来源、运行信息、复盘、预览和评分。脚手架不会推断或补齐缺失事实。
npm run demo:sync -- <id> 按实际文件重算草稿的输入指纹与提示词指纹，在指纹尚未记录时补写评分指纹，并打印导入清单（占位文字、截图、预览入口、embed、评分状态、访问统计引用）。--check 只报告，--finalize 在清单全部通过后把 status 置为 ready。 填写真实输入、来源、运行信息、复盘和评分；把预览入口登记为可嵌入对比页。只处理 status: "draft" 的记录，已入库记录的输入不会被脚本改写。
npm run build:demo -- <id> 仅对 kind: "build" 的实验安装其独立依赖、运行登记命令、复制预览并记录构建指纹。 确认默认入口、Pages 子路径和 iframe 中的真实页面表现。静态 HTML 与外部部署不走这个构建脚本。
npm run review:scores 生成本机临时盲审图集和匿名原图，隐藏模型、档位、日期、费用与旧分。 按案例评分规则逐图看图、写入分数与评语；图集只帮助检查，不自动识图或打分。
npm run generate 更新目录、阅读页、截图指纹和派生图片；生成文件按既定格式写入。 保留源数据和原始 PNG，检查生成 diff 并提交生成站点文件；不手改 assets/generated/。
npm run validate 检查 schema、ID、路径、输入/评分指纹、构建产物、生成文件新鲜度、截图派生资源、阅读页标记，以及本站 CSS 重复闸门。 它不替代实际打开对比页确认主体可见、按截图规则人工评分或核实外部 HTTPS / iframe 状态。

demo:sync 是草稿同步和局部检查工具，不能替代 validate 或浏览器验收。--check 与 --finalize 互斥，避免只读命令意外入库；检查模式输出“待同步”，不会声称已经写入。评分检查复用 scripts/scoring.mjs，rated 与 insufficient 的任一证据指纹失配都会阻止 ready，首次缺失的指纹才由脚本补齐。任务检查项绑定的正文也必须有效。共用正文已被非 draft 记录引用且指纹失配时，脚本拒绝刷新，维护者应恢复历史正文并新建版本。

静态和构建预览检查本地默认页；外部预览检查 HTTPS 地址格式、空 pages 和 null defaultPage，不会要求它具有本地入口。脚本不会联网证明外部页面可访问或允许 iframe。访问统计清单目前仅检查登记的 HTML 产物是否包含公共脚本引用及明显的内联 Google tag；defer、相对路径是否正确、构建源码入口及实际加载行为仍按访问统计验证。

导入执行顺序

  1. 查询已有主题、任务版本与模型。批量重跑先执行 npm run topics:active；模型资料先执行 npm run models:pending，复用已查证记录。相同任务正文优先复用已有提示词版本；脚手架查重只是提示，不会自动合并或证明输入一致。
  2. 用 npm run new:demo -- ... 建立 draft，填入完整输入、来源、日期、执行条件、费用口径和复盘，放入真实源码。未知事实按 schema 留空或 unknown。维护者的部署适配与统计引用写入 changes。
  3. 配置可嵌入预览及公共统计引用。构建型案例执行 npm run build:demo -- <id>；静态案例直接登记入口，外部案例由维护者取得真实 HTTPS 部署地址。实际打开 HTTP、Pages 子路径及对比 iframe；单 HTML 加查 file://，390px 下检查页面溢出，统计请求用拦截或模拟。
  4. 放入真实 PNG 并登记 screenshot，按当前评分规则逐图复核。新任务登记四项任务检查；需要时运行 npm run review:scores 辅助盲审。脚本不会截图、辨认主体或代填分数；已存在的评分证据变化必须重评并留审阅记录。
  5. 执行 npm run demo:sync -- <id> --check 查看缺项，再执行不带 --check 的同步命令。完成缺项和人工预览验收后执行 npm run demo:sync -- <id> --finalize。普通同步允许保留未完成草稿，成功退出不代表可入库；以清单和最终校验为准。
  6. 执行 npm run generate、npm run validate、npm test、node --check assets/home.js、git diff --check；新导入案例按预览要求执行 npm run test:browser 并实际核对对应新入口，既有浏览器用例不会自动覆盖每个新案例的功能。
  7. 审阅并提交源码、元数据、真实截图、生成文档、assets/generated/ 及适用的 previews/。自动派生不是免提交；GitHub 分支提交继续触发 Pages 发布，不增加 deploy 步骤。

样式按页面归属放置：跨页面共用的规则放 assets/polish.css，共用组件（如对比栏）放 assets/site.css，页面专属规则只放该页的样式表 home.css、topic.css / topic-lifecycle.css、compare.css。同一选择器不写在多个文件里；validate 的样式重复闸门保持跨文件重复选择器和同文件完全相同声明都不增加。案例自身的样式仍归对应 run，不需要为导入案例调整本站样式表。

改动首页、主题页或对比页的渲染结果时，tests/browser/style-baseline.spec.mjs 里的计算样式钉子要同步更新：钉子值变化等于页面外观变化，提交信息里写明改了什么。图片槽位宽度变化时，另外核对 sizes 声明与实际渲染宽度一致，声明偏小会让浏览器取到过窄的变体。新增或收紧规则时，同时补一条能自动判定违反的检查（validate 闸门或测试），只有文档没有检查的规则会在下一次改动时失效。

技术索引在 catalog/guides.json 登记 status 与 network。当前示例的脚本、样式无需远程 CDN；Unsplash 与 Skeleton 示例仍需联网加载外部图片，不能标为离线。新增技术示例保持本站导航和 390px 布局，禁止占位 JSX 作为可运行入口。

这些产物与源码一起提交即可静态发布。生成脚本是维护工具，已提交站点无需安装依赖或现场构建。

主题页浏览

主题页默认使用“全部记录”视图，直接列出模型与厂商、接入供应商与工具、档位与轮次、日期、费用、耗时、输入留存和执行模式。桌面使用紧凑表格，手机使用双列记录卡片，关键数据无需展开；费用备注可从费用摘要展开查看。

记录默认按截图评分排序，这是独立于模型排序的一套顺序：评分降序，同分按实验日期降序，再按实验 ID 升序；没有数值评分的记录（unavailable、insufficient）排在有评分记录之后，并且不回落到模型代际排序。评分只在同一任务正文内可比，因此比较以同一任务版本为单位，不同任务版本分区展示。“按模型”视图的模型分组同样按该分组内的最高评分排序。可在“更多筛选”的排序下拉框显式切换为模型代际顺序（sort=model）或实验日期（sort=recent），切换结果写入 URL 并可分享；默认排序不写入 sort 参数。排序规则见评分规则。

“按模型”视图分别按任务版本和模型显示记录数、已覆盖档位及最近登记日期。展开后使用七列语义表格：档位与轮次、日期、接入供应商与工具、费用、耗时、输入与执行模式、操作。各模型使用相同列宽；分组标题使用浅色底，档位使用标签，金额与时长采用等宽数字。展开时隐藏重复的档位摘要与快捷预览。手机在表格区域内横向滑动，档位列固定，页面本身不横向溢出。按档位、工具和执行模式分组，每组直接列出最近三条记录，更多记录通过“查看更早记录”展开；完整输入、费用备注、原始消耗及复盘通过“完整明细”进入实验阅读页。工具或执行模式未记录时保留未知，不推断它与其他记录使用相同条件。分组不表示原始输入一致，也不建立模型重跑的来源关系；原始输入与上下文仍以各条实验说明和对比页为准。

“档位覆盖”查看模型与档位矩阵，任务正文从顶部阅读入口打开。费用摘要始终区分订阅、批次总额、免费、单次金额和未记录，详细口径可展开查看。耗时由 billing.duration 登记，批次在 catalog/batches.json 维护，单次在 run.json 的 billing 中维护；text 保留来源中的时长描述，seconds 记录明确的总秒数，精确值未知填 null。不从备注动态解析、文件时间或订阅额度推断耗时。批次耗时始终显示案例数，不拆算为单案例；历史完整费用快照可以从批次字典补充新增耗时字段，不覆盖原始 run.json。缺失耗时显示“耗时未记录”。手机默认显示搜索和模型，档位与排序在“更多筛选”中。

筛选和视图通过 URL 恢复；view=models、view=list、view=matrix 和既有 view=prompt 均可直接访问。模型展开状态使用 open，历史展开状态使用 history，键来自任务版本、模型及实验条件，不依赖显示名称或列表位置。#run-{实验 ID} 在模型视图中自动展开对应模型和历史，在完整列表中继续定位对应行。

提示词与对比的含义

完整输入只规范换行和 BOM 后计算指纹，不删除空白、模型名称或改写措辞。共同任务正文需要明确提取并在 prompt.json 记录提取方法。原文一致、正文一致、同主题不同输入和跨主题分别标注。多轮追加输入、系统上下文、图片等材料没有留存时标记 partial，不能宣称公平评测。

需要补充新一轮输入或改进实现时，新增实验记录；保留前一次文件，在 environment.notes 和 changes 记录来源、追加输入及人工修改。未知模型、日期、平台不猜测。

对比 URL 只接受目录中的实验 ID，可选择子页面；两侧独立运行，无自动评分。手机只加载当前侧，切换可能重置状态；卸载会释放页面。外部站点嵌入失败时独立打开。双开 WebGL 不能作为单项目性能结论。

模型展示与对比排序

模型展示名称统一由 catalog/models.json 的 label 提供，采用品牌标准大小写、数字版本和空格分隔的变体，例如 GPT-6.1 Sol、MiniMax M2。显示名称修正不改实验 ID、原始输入或历史说明。

模型字典显式维护 provider（厂商）、version（数字版本数组，如 [6, 1]）和 variant（变体，无则为空字符串）。未知模型用 null 厂商和空版本数组，不从实验目录或标题猜测。

对比选择器按厂商英文名称升序分组，未知放最后；厂商内部按模型发布日期与排序使用已登记的代际、同代能力优先级及发布日期。同模型的明确档位按 max、xhigh、high、medium、low 从高到低排列；ultra 等非标准标签随后单独保留，default 再后，unknown 最后。default 不映射为某个固定强度，不推断 ultra 与明确档位的强弱关系。排序统一由 assets/core.js 维护：模型顺序供筛选列表、档位筛选、矩阵列与对比选择器共用；主题页实验记录的默认排序是截图评分，模型顺序需显式选择 sort=model。同档位按实验日期降序、轮次降序，再按实验 ID 自然排序。分组计数反映当前范围和搜索结果；搜索支持显示名称、模型 ID 和厂商。首页模型筛选、侧栏下拉和弹窗使用同一模型排序与厂商分组；侧栏同正文候选用「同正文」标记，不改变模型顺序；上一/下一版本与默认填充采用选择器排序。

档位定义参考 OpenAI 推理模型文档：支持的档位及默认值因模型而异。上述从高到低是本站的浏览顺序，不能作为跨模型性能排名；仅排序已有归档数据，不为历史实验补写档位。

展示名称与 API ID 分开维护：GPT 系列统一为 GPT-版本 变体，变体使用首字母大写；Claude、MiniMax 保留品牌大小写，不对所有品牌机械转成全大写或全小写。档位从 run.json 读取，展示原始档位名与中文说明（如「medium（中）」「max（最大）」），未记录时显示「档位未记录」；轮次显示中文（如「第 1 轮」），原始数据与分享参数保持不变。

浏览与对比工作区

首页、主题矩阵、统一四条选择栏和运行条件表的交互规则见 工作区说明。修改这些交互时同步维护根路径和 Pages 子路径浏览器回归。所有计数与候选仍来自生成目录；截图评分是人工按版本化规则复核，不代表自动代码评分或模型能力。

首页评分与复杂度排序

主题视图固定按任务复杂度降序展示主题，复杂度相同时按最新实验日期和主题 ID 排序；评分、日期和名称排序不会改变主题顺序。每个主题卡片展示该筛选范围内评分最高的测试记录及对应截图和预览。实验记录视图可按复杂度、评分、最新记录与名称排序。评分衡量截图中可见的任务覆盖和呈现质量，不是模型能力或公平性能评测；评分维度、证据、并列规则和版本升级方法见评分规则。没有真实截图的记录为 unavailable；有截图但主产物尚未展示的记录为 insufficient，界面显示“证据不足”，两者均无数值评分，不参与最高分选取。

当前规则为 v2：任务覆盖 40 分（每份任务正文的四项检查各 10 分），构图 20 分、可读性 15 分、操作表达 10 分、完成细节 15 分，逐项独立评定。必须记录截图状态、可见证据与主要限制，并绑定原始输入、截图和任务检查的哈希；更新任一证据后重新审查，validate 会拒绝失效评分。仅未完成且无预览的草稿可用 pending。本次全量复核及旧分留档见2026-10-15 复核报告；后续重评必须保留前次评分快照。

主题复杂度继续在 topic.json 的 complexity 中维护 level（1–5）与 reason。评级依据为已归档任务正文，综合算法与模拟、交互与状态、系统集成：1 为基础展示，2 为常规交互原型，3 为多流程交互，4 为复杂交互或系统，5 为综合复杂任务。复杂度是任务分类，不随截图评分变化；缺失或 null 表示未评级，排在已评级主题之后。

主题聚合时始终按复杂度降序；同级主题按当前筛选结果中的最新实验日期降序，再按主题 ID 排序；无实验日期按空值处理。每张主题卡片选取当前筛选范围内分数最高的实验，评分并列时按实验日期降序、实验 ID 升序。实验记录视图继承主题复杂度，支持复杂度、评分、最新记录和名称排序。排序先于分页，筛选与分享链接保留排序选择；切回主题视图时固定为复杂度排序。默认按主题聚合以集中同任务的模型版本。卡片显示级别，悬停标签可查看依据。

旧首页链接的 sort=latest 未识别时回到复杂度优先；用户明确选择“最新记录”时使用 sort=recent，刷新与分享仍保留日期排序。卡片分类位于左侧，授权、评分、复杂度和归档/预览状态集中在右侧标签组，空间不足时换行。
